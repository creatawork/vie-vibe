# 文章撰写规则

适用范围：发布到个人站点 [Vie](https://vie-vibe.cn) 的系列文章（`docs/articles/` 下所有文稿）。
定位：**技术学习分享**——读者是开发者（也包含潜在面试官），内容以"讲清实现与取舍"为先。
制定背景：第 1 篇文章成稿后经三轮校订，发现并修正了虚构经历、时间夸大、编造论敌、
夸大后果等问题；本规则将其固化为硬性约束，后续文章在成稿与发布前逐条执行。

## 一、禁止虚假内容（红线）

1. **禁止虚构经历与时间**。所有"发生过"的事件必须能在 git 提交、trace 文件或
   计划文档 §8 中找到出处；时间表述以 git 日历为准，不得放大
   （"后来""上周""好几次"这类与项目实际年龄对不上的词禁用——项目第 1 篇文章
   成稿时仓库只存在了三天）。
2. **禁止虚构论敌与引用**。"被质疑过""有人说"必须有真实出处；没有论敌就正面
   陈述决策理由，不要树一个假对象再反驳。
3. **禁止编造数据与输出**。数字（成本、耗时、token、测试数、代码行数、步数）只能
   来自三个出处：trace 实录 > 计划文档 §8 的验收记录 > 实测命令（`wc -l`、
   `pytest --collect-only` 等），写完逐个回查。示例输出必须真实可复现，不得
   "示意性编造"——没有成功运行的任务就展示失败任务的 trace，并如实说明。
4. **禁止把推测写成观察**。未亲自观察到的现象用"可能/通常/一般"表述
   （"可能这次两步、下次三步"✓，"今天两步明天三步"✗）。
5. **禁止夸大后果**。错误与风险的后果按实际影响描述，不得为修辞效果合并升级
   （三个细节里只有一条会被端点拒绝，就不能写"做错任何一条都会被拒绝"）。

## 二、口吻（客观）

1. 用**设计事实**代替**经验宣言**：说"三个消费方各自只需要处理三种事件"，
   不说"这个约定救了我好几次"。
2. 删掉说教式引语（"值得强调的是"）与自我评价（"划得很值"）——观察本身
   有趣不需要预告，设计好不好让事实呈现。
3. 第一人称只允许出现在两种位置：真实做过的动作（"我在等待结果时手动中止了它"）、
   明确标注的观点（"我认为这是最重要的决定"）。
4. 营销词换中性词：卖点→核心设计，杀手锏→关键机制，生死线→关键约束。
5. 口语化拟人（"抽风""脏活"）换中性表述（"不稳定""容易忽略的细节"）；
   适度口语可以保留，以不牺牲准确性为界。

## 三、技术正确性

1. 文中每个协议字段、事件名、文件名、命令行，写完后与仓库逐个核对
   （前后端两侧都查：`erpilot_api/events.py` ↔ `apps/web/src/protocol.ts`）。
2. 代码片段必须与仓库代码逐行 diff；删节显式标注（"此处删了枝节"），且片段
   自洽——不出现未定义的名字，删节不改变语义。
3. 不确定的实现细节：要么查仓库/文档确认，要么明确写"未验证/待验证"。
4. 外部链接以 `git remote -v` 的真实仓库地址为准，发布前全部点一遍。

## 四、发布前核对清单

- [ ] 每个数字能指出出处（trace / 计划文档 §8 / 实测命令输出）
- [ ] 每段代码片段与仓库 diff 过，删节处有标注
- [ ] 全文搜索：后来 / 上周 / 好几次 / 被质疑过 / 救了我 —— 逐一确认有据或删除
- [ ] 时间表述与 git log 一致
- [ ] 文中链接全部指向正确（含仓库名大小写）
- [ ] 通读一遍：把每个断言问一遍"我怎么知道的？"，答不上来的改写或删除
